# Datasheet — BBO Challenge Dataset

**Imperial College London | Professional Certificate in ML & AI | Stage 2 Capstone**

---

## Motivation

**For what purpose was the dataset created?**  
The dataset consists of the query-response pairs accumulated during the 13-week Stage 2 BBO challenge. Each week, one coordinate vector per function was submitted to the Imperial portal, which returned a single scalar output. The purpose was to construct a surrogate model of each unknown function from these sparse evaluations.

**Who created the dataset and on whose behalf?**  
Imperial College London provided the eight black-box functions via the capstone portal. The query-response dataset was accumulated by Srini Rajasekaran through weekly portal submissions during Modules 12–24.

**Who funded the creation of the dataset?**  
Imperial College London, as part of the Professional Certificate in ML & AI programme.

---

## Composition

**What do the instances represent?**  
Each instance is a single oracle evaluation: a coordinate vector (the query) and a scalar output (the function value returned by the portal). There are no features beyond the input coordinates and the returned output value.

**How many instances are there?**  
Initial datasets provided by Imperial + 13 weekly queries per function. Total observations per function at campaign end:

**Does the dataset contain all possible instances?**  
No. These are sparse point evaluations of continuous functions defined on the unit hypercube [0, 1]^d. The true functions are never fully observed.

**Is there any missing data?**  
No. Every submitted query received exactly one portal response. No missing values.

**Does the dataset contain confidential information?**  
No. The input coordinates are chosen by the analyst. The output values are generated by the Imperial portal. No personal or confidential information is involved.

**Does the dataset relate to people?**  
No. The functions are mathematical optimisation targets. Some have real-world analogues (chemical yield, warehouse allocation) but the data itself is synthetic.

## Collection Process

**How was the data associated with each instance acquired?**  
Queries were submitted manually by Srini Rajasekaran to the Imperial capstone portal. The portal returned a single floating-point scalar for each query. No automated scraping or batch submission was used.

**Over what time period was the data collected?**  
Modules 12–24, approximately June to August 2026. One query per function per week.

**Were there any errors, missing values, or outliers?**  
One F5 initial data point (y = 1,088.860) was approximately 700× larger than the next-highest initial value. This was a genuine function feature — the initial design happened to sample a high-yield region. All other function distributions had no implausible values.

## Preprocessing and Cleaning

**Was any preprocessing applied?**  
For GP surrogate fitting: outputs were standardised (zero mean, unit variance) within each session. For regression analysis: inputs were standardised (zero mean, unit variance) using the full combined dataset. No preprocessing was applied to the raw portal outputs stored in the data files.

**Is the software used to preprocess the data available?**  
Yes. See `stage2_bbo/src/data_loader.py` for the combined dataset construction and standardisation logic.

## Uses

**Has the dataset been used for any tasks already?**  
Yes. It was the primary training data for Gaussian Process surrogates (RBF, Matern-3/2, Matern-5/2 kernels) fitted weekly to inform the next query. It was also used for OLS regression analysis, KDE density estimation, k-means clustering, Nadaraya-Watson regression, XGBoost + SHAP analysis, PCA decomposition, and bootstrap resampling.

**What other tasks could the dataset be used for?**  
As a benchmark for surrogate modelling under extreme data scarcity (n/d ratios of 5 to 11). The F4 function's catastrophic roughness (observations within Euclidean 0.05 spanning -11.6 to +0.49) and F1's sub-0.014 spike width are particularly challenging test cases for surrogate reliability.

**Are there tasks for which the dataset should not be used?**  
The dataset should not be used to draw conclusions about the real-world systems the functions nominally represent (chemical yield, drug formulation, warehouse logistics). The true variable meanings are unknown; the function labels are illustrative analogies provided by Imperial.
